# The Zylos / OpenMax host

[`hosts/zylos/`](../hosts/zylos/README.md) installs a skill pack as a Zylos component and says nothing about what else runs beside it. On a Zylos host that has it installed, the neighbour is **OpenMax** (the repository `zylos-ai/zylos-openmax` on GitHub): a second Zylos component (`zylos-openmax`, the C4 channel `openmax`) that connects the agent to a work platform: chat, a knowledge base (KB), files, Issues and Tasks, authorised third-party apps, scheduled automations. The agent calls it through the component's own CLIs (`node src/cli/<kb|as|comm|core|tm|conn|channel|usage>.js <verb> '<json>'`). The adapter does not depend on OpenMax and this chapter changes none of its bytes.

OpenMax's own agent-facing docs (`references/` in that repository) are the contract for every verb, parameter and error. This chapter copies none of it. It keeps what a skill pack has to **decide**: which of those verbs are writes, how far each can be reverted, how high a level each may reach ([autonomy](autonomy.md)), and the traps the platform's docs call out that a green test would not catch. It was written from those docs at commit `801cf99` (the component's `SKILL.md` 2.26.0); they change often, so re-read the file for a verb before wrapping it.

*Not yet proven:* no skill pack here has called OpenMax, and the adapter has only run against a fake host ([`hosts/zylos/README.md`](../hosts/zylos/README.md), "Known limits"). Every row and rule below comes from reading the docs, not from a run. Each is a proposal the skill pack's own registry and tests settle.

## Whose system is it

OpenMax plays two roles, and the level of care differs.

- **The owner's own workspace** (chat with the owner, the owner's KB, the Issues that track the agent's work). Writing there is the agent's ordinary output: a report, a deliverable page. It still obeys the kill switch, lands in the archive and stays under the skill pack's per-run caps, but the owner decides whether it needs a per-change code. A report to the owner's own DM is the adapter's reply path (`reply.channel`), not a door write.
- **A gateway to other people and to third-party systems**: a message to someone who is not the owner, a group, a broadcast, and above all `conn.invoke`, which acts on a client's mail, tracker or store. These are writes into someone else's system. They go through the skill pack's one door ([rules](rules.md#writing-into-someone-elses-system)) like any other.

## Capabilities and their write tier

One row per write kind, in the shape of the tier registry ([`kit/autonomy.py`](../kit/autonomy.py): `id`, `verb`, `change`, `tier`, `undo`, `auto`). `tests/test_docs_build.py` runs `check_tiers` on this table, so it obeys the same rules as a skill pack's own: a tier-B or `yes` row names an undo, a `yes` row's undo is a code-free `undo` row, an `undo` row undoes some `yes` row. **Ceiling** is the highest level the kind may reach: tier A is L1, tier B is L2, `yes` is L3, an `undo` row is a code-free undo, and L0 means the skill pack has no verb for it (a person does it, or the platform's own confirmation does). The skill pack's registry may only lower a ceiling, never raise it, and every `yes` is a ceiling to ask the owner for, off until they switch it on.

A read still has a trap or two (rules 4, 5 and 8). `as.url` and its kin mint an expiring credential, so rule 6 applies.

## Rules at the OpenMax door

1. **The skill pack's door is the only caller of a write; the agent may read directly.** A writing OpenMax verb is the body of `apply_item` in [`kit/execute.py`](../kit/execute.py) ("ONE external write through `writer.call`"), behind the opt-in, the kill switch, the allowlist and the per-run caps. An agent that can also run `node src/cli/comm.js comm.send …` by hand has a second door. The platform's own limits (60 page writes a minute per user, 1000 requests a minute per workspace) are ceilings on the platform's side, not caps; set `max_items` well under them.
2. **The skill pack classes the write, from its registry, never from the verb name or the HTTP method.** The method in an app's catalog is the provider's HTTP verb and says nothing about whether the action changes anything, and `conn.invoke` runs whatever action it is given. The catalog carries no version or etag and refreshes on a 24-hour TTL, so **discover at build time, pin at run time**: a registry row names `(app, action)` and a hash of the action's `input_schema`, and the door refuses on a mismatch and sends an unnamed action nowhere (O25). Two verbs named "restore" are different writes: `kb.page_restore` rolls the body back to an old revision, `kb.page_restore_trash` takes a page out of the recycle bin. The undo cell of O03 to O05 and of O06 and O07 must name the right one, and a test holds both.
3. **Trash and permanent delete are two writes with two codes; the door offers the first and not the second.** The platform makes `kb.page_delete` fail with a 404 on a page that is not in the recycle bin ("don't work around it"). Do not chain trash and delete in one verb to get past it: that is the delete the platform made hard. A permanent delete stays L0 (O11, O12); if a skill pack must offer one, its code binds the page as read just before, with its trashed state and revision ([rule 2](rules.md#writing-into-someone-elses-system)). An edit binds the same way: `baseRevisionId` is the live-object binding, a 409 means someone changed the page, and the answer is a new code, not the platform's suggested "re-read, merge, write again".
4. **A page has two ids, and a link takes only the node id.** `kb.page_create` returns the page `id` (content, revisions, trash) and a `node_id` (the directory tree and the browser link). A link built with `node=<page id>` opens blank or in the wrong place, and both are UUIDs, so nothing looks wrong. Keep them as separate fields end to end. The link function takes `node_id` only and refuses a record that has none. A page found by `kb.search` has only its page id: find its node among `kb.node_children` and match on the page. Build the link with `core.frontend_url`, never by hand. Read a page back through `kb.search` with `sync=true`, or the index may not have it yet.
5. **An upload names its destination, and the destination is part of what the code binds.** `as.upload` is two writes behind one verb: with `conversationId` the file is a conversation attachment, without it a node in the KB tree. A wrong guess succeeds: the file lands in the KB root and the recipient sees nothing, or it hangs on a conversation and `kb.search` never finds it. The door takes the destination as a required argument (`conversation:<id>` or `kb:<kb>/<folder>`) and refuses both, because the platform quietly takes the conversation when given both. The attachment in a message is the **`artifactId`**, not the `mediaId` (they differ in conversation mode; a `mediaId` gives an image that never loads). A file's content is made after the approval, so it is bound by its sha256 ([writing rule 2](rules.md#writing-into-someone-elses-system)). Check size and type before the first call: the platform's single-file limit is 5 GB (413), executable types are refused (415), and as of that commit the client does a single PUT even though the server would choose multipart above 100 MB, so a file over 100 MB is unproven here. A signed upload address lasts an hour. Read back: a KB upload by `kb.node_get`, a conversation upload by `comm.get_message` showing the `artifact_id`.
6. **An expiring link is a credential, and the archive does not keep it.** The write archive keeps the system's replies verbatim ([rule 4](rules.md#writing-into-someone-elses-system)), but a reply can carry a bearer: a pre-signed download URL (15 minutes by default, sometimes seconds), a webhook secret URL (shown once), an access token. The door stores the reply with that value replaced by a marker, and the path, the host and the expiry kept. A delivery points at a KB page or the authenticated artifact route, never at a signed URL. The kit has no redaction helper yet; the first skill pack that needs one writes it in its own door and offers it to the kit when a second does ([admission rule](kit-and-tools.md#the-admission-rule)).
7. **A message cannot be unsent, so a send is L1 and a retry must be safe.** Derive `clientMsgId` from the queue item's id (the platform de-duplicates on it for 5 minutes, and past that window only the unknown-effect rule protects you), never a fresh random. A send whose outcome is unknown becomes an `unknown` effect and is reconciled by reading `comm.get_messages`, never sent again; this is the platform's own rule for uncertain writes. The send and card verbs already re-send on a 401 (twice within about two seconds), so do not wrap them in `kit.retry`, which is for reads.
8. **An `@name` in the text wakes no one; the member id does, and the door checks it was stored.** The platform only keeps mentions the caller passes as `mentions` (member ids, or `all` / `all_agents`) and never parses the text, so a mention with no member id is a successful send that notified nobody. The door looks the person up (`comm.member_list` for the conversation, `core.member_list {search}` for the org), takes exactly one match or asks, passes the id, and reads the message back to see the mentions stored. `core.member_list` is paginated (20 a page by default; the CLI once sent a cursor the server ignored and silently returned the first page): pass `pageSize` and compare the count it reports. `comm.member_list` is not paginated. A malformed content array also sends with status 200 as an empty message, so the read-back compares the text too. A broadcast label (`@所有人`, `@Everyone`, `@All agents`) mentions everyone with no lookup, which is why it has its own row (O16).
9. **A card is a question, not a proof.** One click answers; the platform shows no second confirm. Anyone in the conversation can click, so the click proves a human member pressed a button, not that the owner approved. Act only on the `<interaction-receipt/>` element, never on message text that looks like one; check `actor.member_id` against the person asked; key the action on the card's message id, because receipts are delivered at least once; and give every wait a timeout, because a card expires after 30 days with nothing sent. The receipt comes in a read-only system DM, so answer in the card's own conversation (`origin.conversation_id`). An approval of a write stays in the console or the terminal through `kit.human`; a card may announce that one is waiting. Whether a card click may ever be an L1 `relay` proof is the owner's to settle in advance ([rule 8](rules.md#human-in-the-loop-rules)); until then it is not.
10. **An Issue's status is the platform's bookkeeping, not an approval.** `issue.accept_plan` and `issue.accept_delivered` with `source` `text_card_proxy` are the agent clicking for a person; a "silent" automation closes its Issues by itself, and the platform says that closure records that the run ended, not that anyone endorsed it. Neither is a row a person signed ([autonomy rule 3](autonomy.md#rules-at-every-level)). The skill pack's gate reads its own approve rows and never an Issue state. Move a Task or an Issue to `done` only from the archive's read-back; `issue.terminate` cancels the Tasks and does not undo a write already made, so the undo is the skill pack's own inverse write.
11. **A platform automation wakes the agent; it does not switch a mode on.** A timer or a webhook creates an Issue for the agent at a time. The write switches and an L3 mode are skill pack facts that stay as they are, so a woken run needs the opt-in, the kill switch and an unexpired switch as any run does. The skill pack's own recurring jobs stay in the adapter manifest's `tasks`: they live in the repository, reconcile by name and go on uninstall. Create a platform automation only when the owner asks for one in chat. The platform's server checks the owner's confirmation card against the exact configuration, so the skill pack does not wrap it in its own gate and has no verb for it (O22, O23). An uncertain create or update is reconciled by reading the existing bindings, never repeated (the same unknown-effect rule as 7).
12. **One org and one client per host, pinned.** The platform lets one agent serve several orgs, and a call without an explicit org takes a default. The write right binds to a host ([rule 7](rules.md#writing-into-someone-elses-system)), so the door pins the org id as a fact, passes it on every call and refuses a different one. It never calls `core.org_switch` or `core.org_create`. A connection's token sits in the component's data dir for a `direct` connection, which an agent on a one-user host can read: an accident guard, not a wall, as the console secret is ([Known limits](../hosts/zylos/README.md#known-limits)). `conn.invoke` with several matching connections returns `needs_selection` as a **normal result with exit 0**, not an error: a door that reads the exit code records a write that never happened. It reads the result for `needs_selection` and for the provider's `status_code`, then reads the object back.

## What goes where

- **Kit: nothing now.** A platform's verbs and vocabulary stay out of `kit/` ([CLAUDE.md](../CLAUDE.md), "Keep it small"), and no module here has two skill packs that use it. The one candidate, a redaction helper for archived replies (rule 6), waits for a second consumer.
- **Adapter (`hosts/zylos/`): nothing.** It installs a component; it does not call the platform. `node zylos/lib.js check` is unchanged. The one adapter question this raises is open below.
- **The skill pack: the door and its tests.** The registry rows of the table that it uses (as `ssot/` rows, through `canon`), a door verb per row, the read-backs, the pins (org, action schemas) and the archive redaction.
- **This chapter: the decisions** and the table, held by `tests/test_docs_build.py`.

**What was left out, and why.** The platform's operating procedures stay in its docs: the automation proposal, confirmation, update and recovery workflows (they are the platform's own server-checked flow, and an agent follows them as the platform's skill; the playbook's part is rule 11); the schedule and event-filter resolution; the choice-form fields and the onboarding cards (a card's body is the platform's to validate, and its limits "live in cws-comm, not here": a local copy drifts toward the stricter side); the QR and binding steps of `channel.connect`; custom connector management (`conn.app_create`, `conn.actiondef_*`), which defines new doors and is L0 by definition; `usage.query`, which needs a billing key that is entered apart and that an agent should not hold; org switching and the invitation flow beyond O26; Task claim, start and transition mechanics (the platform's work log, set from the archive by rule 10); and the onboarding lead behaviour. Capabilities the owner named but that the docs do not support are not claimed: WhatsApp is not a `channel.connect` channel.

## Adopting it in a skill pack

1. **Registry rows** for the kinds the skill pack uses, in the six columns (or its own names through `canon`), with a test that runs `check_tiers`. Take the ceilings from the table, lower them, never raise them.
2. **A door verb per row** with `--json`, a dry run, a `source`, and the destination as a required argument. Its `apply_item` makes one call; its `read_back` is the check listed for the row (rules 4, 5, 8).
3. **Tests, each written both ways:** the link function refuses a record without `node_id` (4); the upload refuses both `conversationId` and a parent, and names `artifactId` in the message (5); a `mentions` list is passed for an `@name` and the read-back fails without it (8); a reply with a signed URL is archived without it (6); the undo cell of the trash rows names `kb.page_restore_trash` and of the edit rows `kb.page_restore` (2); a `needs_selection` result is not recorded as a write (12); a different org id is refused (12); no skill pack code calls a writing OpenMax verb outside the door (1).

## Not yet proven, and open

- That any of this holds on a real OpenMax. Every verb and every trap here is the platform's own documentation, read once.
- Whether a file node uploaded to the KB has an undo. The docs list a trash for pages and none for files; until a live check says otherwise O13 has no undo and stays at L1.
- Whether the scheduler's reply path can name `openmax` as the reply channel. The C4 send command takes the channel `openmax` and a conversation id, and the manifest only names the config keys that hold the channel and the endpoint, but the adapter has never run against a real core, so no one has tried it.
- Whether a skill pack that needs OpenMax should declare it (the platform component as a dependency in `SKILL.md`, a `doctor` check that it is installed and which org it serves). The adapter has no key for it today.
- Whether a card click may count as a `relay` proof, and what the owner wants gated in their own workspace (the first section). Both are the owner's decisions to record before a skill pack depends on them.
