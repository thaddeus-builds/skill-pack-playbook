# 设计:发出请求后等回复,并限制追问的轮数

*给负责人看的一页。负责人已按图同意(2026-10-30)。没有演示页:命令行里用的工具。*

## 它是什么

`kit.bridge` 原来发完就结束。现在多两样:`wait_for_reply` 只读地看群,直到有人回复刚发的那条消息,或超时;`next_round` 把追问限制在三轮以内,并且每次追问都要写明"上一轮缺什么"。**回复答没答完,仍由会话里的 agent 判断**,代码只判断"有没有回复"和"能不能再问"。

## 怎么判断"这是回复我的"

真实的群里看到:只有机器人的自动应答带 `parent_id`;agent 的正常回复多数是 @ 提问的人,有的什么都不带。所以一条消息算回复,当且仅当它在我们那条之后、不是我们自己发的,并且满足其一:挂在我们那条下面、@ 了我们、或来自我们问的那个 agent(调用者传 `from_ids`)。"我们是谁"取自我们那条消息的发送者,不用配置里的身份编号(两者在群里不是同一个值)。

## 状态

| 状态 | 含义 | 之后 |
|---|---|---|
| `replied` | 有回复,原文按先后顺序返回 | agent 判断答完没有;没答完且 `next_round` 允许,才追问 |
| `timeout` | 到时间没人回(默认 30 分钟,每 60 秒读一次) | 报告一次,不重发,不接着等 |
| `unreadable` | 连续三次读不到,或找不到我们那条消息 | 报告原因 |

对面离线、被禁止私信:没有可用的在线状态接口,不在代码里判断;表现为 `timeout`,按 `docs/support-channel.md` 第 5 节处理。

## 风险与它的答案

| 风险 | 答案 |
|---|---|
| 两个 agent 互相追问下去 | `next_round` 最多三轮,没有写明原因不放行 |
| 等回复花模型额度 | 只读 HTTP,没有模型调用;包把它放在后台运行,到了再通知会话 |
| 把无关的消息当成回复 | 必须在我们那条之后、非我们发的,并满足上面三条之一;测试覆盖每一条 |
| 群里消息太多,回复被挤出读取窗口 | 一次读最新 100 条;超出时只会表现为 `timeout`,不会误判有回复 |
