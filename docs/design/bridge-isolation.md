# 设计:多个桥同时使用 —— 隔离,以及发送不再经过模型

*给负责人看的一页。看完回一句"同意"即可;不同意的地方直接说。没有演示页:这是命令行里用的工具。*

## 要解决什么

一个技能包的 agent 会同时碰到:一个会话对一个组织说话、同一个会话想再对另一个组织说话、几个兄弟会话各对各的组织(或对同一个组织)说话。`kit.bridge` 现在每发一条消息要 `claude -p` 起一个完整的桥两次(发送、读回),每次都是一次模型调用,并且给同一个身份多开一条连接。读插件源码后的隐患(未实测):同一个身份多连接会共用令牌缓存和同步游标;没设数据目录时所有桥共用一个目录;playbook 没有任何文档、模板或检查提到数据目录。

## 三个方案

| | A. 继续 `claude -p`,补隔离 | B. 直接调 REST 发送,不起 claude | C. tmux 里常驻一个会话,用 send-keys 驱动 |
|---|---|---|---|
| 每条消息的模型调用 | 2 次 | **0 次** | 每次 1 轮以上 |
| 对桥的占用 | 每次一条新连接 | **无连接,不碰数据目录和游标** | 一个会话,多个包要排队 |
| 跨设备 | 每台装好插件 | 只需一个配置文件(密钥不进 git) | 每台装 tmux,并保持会话活着 |
| 并发安全 | 靠文件锁,服务器行为未知 | **天然无冲突**(只是 HTTP 请求) | 排队,但一个卡住全卡住 |
| 本机现状 | 可用 | 可用(Python 标准库) | **没装 tmux** |

**推荐 B。** 用量上看:最近 30 天有 626 个会话文件(最近 7 天 213 个),分布在 142 个目录,大量并行。发送这种确定性的动作不该花模型额度,也不该占一条连接。收信(被 @ 唤醒、让 agent 回答)仍用交互桥,这是插件本来的设计,每个身份**只在一处**常驻。tmux 只用作无人值守设备上"常驻收信桥"的外壳,不进 kit,也不在这次的改动里。

## 它怎么工作

1. 用配置里的 `api_key` 换一个组织级令牌(`POST /auth/agent/token`,带 `org_id`)。
2. 发送:`POST /conversations/<id>/messages`,带 `type` 和 `content.body.text`(带类型的正文,不是纯字符串;`docs/support-channel.md` 记过纯字符串会返回 422)。
3. 读回:按返回的消息编号再读一次,和想发的内容比较。规则不变:空或不同则重发一次,没返回编号不重发,读回失败不重发。
4. 令牌只在内存里,不写盘;不使用也不改动数据目录。

## 风险与它的答案

| 风险 | 答案 |
|---|---|
| REST 路径或字段与插件实际用的不一致 | 合并前用真实的桥做一次只读验证(读已发的那条消息),再在你同意后发一条测试 |
| 密钥进了日志或 git | 令牌与密钥不进任何返回值和日志;配置路径只来自包在仓库外的配置;测试里用假服务器和假密钥 |
| 两个包同时发给同一个组织 | 按发送返回的编号读回,不读"最新一条";REST 没有会话状态,不会互相覆盖 |
| 配置或数据目录写错导致发到别的组织 | `check_isolation` 在发送前核对配置里的组织编号与目标一致,不一致就拒绝 |
| 一个包也用不上就留在那 | `bridge` 包本就是孵化中(到 2026-12-31),这次不改日期 |
