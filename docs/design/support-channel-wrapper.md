# 设计:往客户 agent 发消息的"发送并核对"工具

*给负责人看的一页。看完回一句"同意"即可;不同意的地方直接说。没有演示页:这个工具不写给人看的页面,只在命令行里用,所以没有可点的东西。*

## 它是什么

一个小命令:把一条消息发进客户的支持群,然后**自动再读一遍**,确认发出去的内容和想发的一样,再告诉你"已发送"。现在这三步是人(或 agent)照着 `docs/support-channel.md` 手动做的,Google Ads 和 Meta Ads 两个包都遇到过"桥说成功了,但存进去的是空消息"。工具把这个检查变成不可跳过的步骤。

## 它怎么判断

1. 只发一条普通文本,`@名字` 一律用英文 `@`。
2. 发完拿到桥返回的消息编号。
3. 另开一次只读调用,按这个编号把消息读回来。
4. 读回来的文字和想发的完全一样:报告"已发送",附编号。
5. 是空的或不一样:再发一次,最多一次,并说明这是重发。第二次还不对:停下,报告失败,不再发。
6. 桥没返回编号:视为没发出去,不重发,直接报告(避免重复发给客户)。

例子(虚构):想发 `@DEMO-support 请确认 DEMO 账户的时区`。桥返回编号 `DEMO-17`,读回来是空的 → 重发 → 编号 `DEMO-18`,读回来一致 → 报告"已发送(重发一次,第一次存成了空消息)"。

## 它存什么

不存任何表。一个"最后看到的消息编号"文件,放在包的配置里、不进 git(已在指南里说明)。

## 风险与它的答案

| 风险 | 答案 |
|---|---|
| 读回时群里别人也在发言,读到别人的消息 | 按发送返回的编号读,不读"最新一条" |
| 重发导致客户收到两条 | 只在读回为空或不同时重发,最多一次;没返回编号时不重发 |
| 测试需要真实的桥 | 不需要。用假的桥回答写测试,其中一个就是"存成空消息" |
| 客户信息进了 git | 工具不带任何客户名、群编号;这些只来自包在仓库外的配置 |
| 一个包也用不上就留在那 | 在 `tools/pack_status.tsv` 登记为"孵化中",写明日期;到期两个包没有都引用就删除或移回 |
