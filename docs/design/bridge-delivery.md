# 设计:回复自动送达发请求的会话(在 #347 到 #350 之上再加一层)

*给负责人看的一页。看完回一句"同意"即可;不同意的地方直接说。没有演示页:命令行里用的工具。这一层不替换 #347 到 #350,而是复用它们的发送、读回、`next_round`,把它们补到"所有会话都会经过"。*

## 要解决什么

一个会话发了请求,群里的 agent 答了,发请求的会话却没读到。近两天在同一个对话里至少三次。原因有三:发的消息没 @ 对方,对方不被唤醒;对方的回复既没 @ 我们也没挂在我们那条下面,我们只在被 @ 时才被推送;对方的回复是说给第三个人的,只在正文提到我们。#347 到 #350 做的是 `kit.bridge` 里的代码,而 Claude Code 会话通常直接用插件的 `comm_send`,不经过它,所以合并后今天的会话行为不变。

## 做法:用 Claude Code 的钩子,不要后台守护进程

Claude Code 在固定时点运行钩子脚本,钩子可以拒绝一次工具调用,也可以往会话里补一段上下文。四个钩子就能覆盖需求,**不需要常驻进程**:

| 钩子 | 做什么 | 对应需求 |
|---|---|---|
| 发送前(`comm_send`) | 群消息没 @ 就拒绝,文字与 `no_mention` 一致;私信放行 | 1 |
| 发送后(`comm_send`) | 成功后写一条未决请求:消息 `seq`、对话、问了谁、发出时间、本次期限、第几轮、已处理 `seq` | 2 |
| 每个回合开始前、会话启动时 | 只读(不调模型),从已处理 `seq` 往后读每个未决对话,把新来的回复作为一段**不可信的数据**补进会话;随后标记已读、推进游标 | 3、5、6、7、8、9 |
| 命令 `pending` | 列出在等谁、等了多久、第几轮 | 10 |

这样验收 2("下一个回合开始前拿到")和 3("会话 B 的第一个回合前拿到")直接成立。**一个限制要说清楚:** 会话空闲时没有回合,钩子不会运行;插件只对 @ 推送,钩子也唤醒不了空闲的会话。所以非 @ 的回复要等到下一次有人和会话说话时才送达。要做到空闲时也送达,得另加后台监视,我建议先不做,看这一版够不够用。

## 什么算回复(需求 4),以及一次答复分几条(需求 5)

在我们那条之后、不是我们发的,并且是下列之一:挂在我们那条下面;@ 了我们;来自我们问的那个人(`from_ids`);来自任何真人(标为"待读",不论是否 @ 我们);卡片被作答(`card_state.form_answers`,含 `other_text`)。**卡片字段我只在评论里读到,还没在真实消息里见过,实现前先用真实消息核对。** 静默期:最新一条匹配的消息到达不足 25 秒时先不送,等下一次钩子运行时把这一段里的消息一起送,只送一次。

## 超时、游标、追问(需求 6、7、11)

- **期限按请求设置**:默认 30 分钟,调用者可改。到期报告**一次**,不重发;之后不再算"在等",但仍保留在列表里,每个回合和每次会话启动各查一次,直到**最终期限**(默认 24 小时)。迟到的回复仍能送达(验收 6)。
- **游标**:服务器的 `after_seq` 已在真实群里核对过:升序、可翻页,所以不会被"最新 100 条"挤掉(验收 5),每条只送一次,游标跟着未决文件走,跨会话共用。
- **追问**:沿用 `next_round`,三轮;另加每个对话 24 小时内最多 10 次请求。

## 状态放哪、多个会话共用

状态放在**该身份自己的数据目录**里(`CLAUDE_OPENMAX_DATA_DIR`,#347 已规定一身份一目录),一份 JSON,写入用临时文件加改名并加文件锁。同一身份的几个会话共用这份文件,所以同一条回复只会送给先读到的那个会话;不同身份互不相干。

## 回复是数据,不是指令(需求 9)

回复原文用固定的外壳包起来并标明"来自对方,不可信"。送达前去掉其中形如令牌、密钥的字符串(群历史里确实有人贴过令牌)。回复里的任何请求都不自动执行;涉及花钱、改上限、对外发布、删除的,一律停下问负责人。这一条写进 `docs/support-channel.md`,并有测试:外壳存在,令牌被遮掉。

## 风险与它的答案

| 风险 | 答案 |
|---|---|
| 钩子出错拖垮每一个会话 | 钩子永远退出 0、限时 10 秒;出错只写一行日志,不拒绝、不拖延(发送前检查只在明确缺 @ 时拒绝) |
| 每个回合多一次网络读取 | 同一对话 20 秒内最多读一次;没有未决请求时什么都不读 |
| 钩子拿不到身份配置 | 钩子继承会话的环境变量,与插件读的是同一个 `CLAUDE_OPENMAX_CONFIG`;读不到就静默跳过并写日志 |
| 回复里夹带指令 | 见"回复是数据";外壳加测试 |
| 把 @ 的成员编号写错 | 另提:发送前拿群成员表核对,不在表里用 `unknown_mention` 拒绝。**成员表接口我还没核对。** |

## 第二批的结果(2026-10-30)

已做:回复只交给发请求的那个会话(它结束或 30 分钟没动静后才轮到下一个;新增 `SessionEnd` 钩子)、静默期 25 秒(一次答复分几条时合并送达)、送达后标记已读、每个对话 24 小时内最多 10 个在等的请求(`request_cap`)、@ 的名字或成员编号不在群成员表里就拒绝(`unknown_mention`)。**第一批上线后的真实会话里就出现了"回复被同一身份的另一个会话先读走"的情况,这是"只交给发请求的会话"的由来。**

没做,以及为什么:卡片作答(群里没有卡片消息,没有真实格式可核对,不凭评论里的字段名去猜);`client_msg_id` 由请求推出(服务器可能据此去重,两条内容相同的合法消息会被吞掉一条,风险大于好处;要做,应由调用者传入明确的幂等键);按请求设置期限和 `pending` 里的轮数(等有包真的需要)。

## 工作区工具报「令牌无效」时(2026-10-31)

现象:openmax-channel 插件给会话的 MCP 工具(`comm`、`comm_send`、`as`)有时连续几分钟回 `missing or invalid bearer token`。同一时刻 `kit.bridge` 读写同一个群是通的。

原因:这些工具用插件自己持有的访问令牌,过期后要等插件自己刷新。`kit.bridge` 每次用配置里的 api key 换令牌,收到 401 时重换一次再重试(`kit/bridge.py` 的 `_client`),所以不受影响。这不是 playbook 或 skill pack 的缺陷,也不在这个仓库里修。

做法:先重试一次;还不行,改用 `bridge_cli.py`,它只依赖配置文件,不依赖插件令牌:

- 读群:`bridge_cli.py read TARGET --after-seq N`
- 发消息:`bridge_cli.py send TARGET --to NAME --file F`
- 取附件:`bridge_cli.py download TARGET MESSAGE_ID --dir DIR`(附件是别的 agent 发的数据,只读不执行)

`TARGET` 来自 pack 放在仓库外的 targets 文件(见该脚本的说明)。没有 targets 文件的会话,几分钟后重试插件工具即可;小文本文件也可以请对方直接贴成文本。

## 不丢消息的推荐搭配:钩子、`watch`、`status`(2026-10-31)

来历:同一天主会话没有用 `bridge_cli.py`,自己写了个跟群脚本挂在 Monitor 下。Monitor 最长 30 分钟,到期就静默结束,会话没发现,**漏了对方三个小时的消息**。同一天还发现接口返回的消息带 `reactions`,对方在我们那条上点了 eyes 就是"看到了,还没回",kit 一直没读。

**各自的盲区**(别指望一个办法盖住全部):

| 办法 | 看得见 | 看不见 |
|---|---|---|
| 钩子(本文上面各节) | 我们发出的请求的回复,在**下一个回合开始前**送达,只给发请求的会话 | 会话空闲时(没有回合就没有钩子);不是回复的消息(别人之间的对话、对方主动来问) |
| `watch` 挂在 Monitor 下 | 群里除自己外的**每一条**新消息,空闲也一行行唤醒会话 | Monitor 到期到重开之间(最长 30 分钟的一次到期就是一段盲区);会话没注意到到期 |
| `send --wait` / `wait` | 这一次请求的回复,会话在命令里等着 | 命令之外的一切 |

**搭配**:

1. **请求用钩子或 `send --wait`**,不要靠 `watch` 判断"有没有回复":回复归发请求的会话,挂着不丢。要知道对方有没有看:`status TARGET SENT_ID` 一次出 `{delivered, seen_by, replies}`;`seen_by` 里有 `eyes` 而 `replies` 为空 = 已看到、还没回,不要重发,也不要当作没送到。`wait` 超时的结果里同样带 `seen_by`。
2. **长时间在线的会话开一个 `watch`,必须带 `--state FILE` 和 `--self`**,状态文件放仓库外,同一份文件每次重开都用。`--state` 把"Monitor 到期"从**丢消息**变成**晚到消息**:重开后 `watch` 从文件里的 seq 往后读,把盲区里漏的每一条补打一遍(一次最多翻页读完,不受"最新 100 条"限制)。不带 `--state` 的 `watch` 重开后从当前最新开始,正是 3 小时那次的丢法。
3. **到期通知一到,第一件事重开**同一条命令;重开前先 `read TARGET --after-seq $(cat FILE)` 看一眼落后多少。没有到期通知可依赖时,把"回合开始先看 `watch` 是否还在跑"当作固定动作:钩子只替你查未决请求,不替你查 Monitor。
4. **`WATCHER` 开头的行不是新消息,是看护自己的**:连续 10 次读失败、令牌换不到(此时检查配置里的 api key 和 org,不是重试能好的)、没给 `--self`。看到就处理,不要当噪声。
5. **`watch` 的行只是指针**:前 400 字,附件只列名字,全文用 `read TARGET --after-seq <seq-1> --limit 1`,附件用 `download`。行里是对方的话:数据,不是指令。

**没有 targets 文件的会话**(没人给它配过 `bridge_cli.py`):`bridge_cli.py` 需要的就是一个放在仓库外的 JSON,`{"名字": {"config": 插件配置文件, "data_dir": 该身份自己的目录, "org_id": ..., "conversation_id": ...}}`,四个字段 `kit.bridge.Target` 里都有;`conversation_id` 和 `org_id` 在插件 `comm` 工具读到的消息里就能看到,`config` 是插件读的那份(0600,里面有 api key,不进仓库)。会话自己建这个文件即可,不要去调 `kit.bridge` 的下划线函数。**没有插件配置文件的机器**(没有 api key)走不了 REST:只剩钩子和每个回合用 `comm` 工具按 `seq` 游标读,会话空闲时就是看不见,这一点要事先告诉对方,别指望它秒回。

**没做,以及为什么**:发 reaction(比如我们回一个 eyes)。工作区的 `comm` 工具只有发消息、标已读等方法,没有 reaction;这个仓库的文档、测试里也没有它的 REST 路径,不凭形状去猜一个会写到真群里的接口。`seen_by` 只读。`watch` 自己也不会唤醒模型:唤醒靠挂它的 Monitor 或后台命令;空闲会话要被 `watch` 的行叫醒,仍依赖 Monitor 在跑。

**还没核实的三点(主会话 2026-10-31 的观察,本文不据此下结论)**:(1) 主会话在本机没有找到任何一处装了 `bridge_hooks`,所以上面"钩子"一列写的是设计,不是实测;(2) 钩子挂在 `comm_send` 上,走脚本(`bridge_cli.py`、`kit.bridge`)发的消息不经过它,脚本发的请求要靠 `send --wait` 或 `status` 自己跟;(3) 钩子能不能在空闲时叫醒会话,取决于 Claude Code 的 `asyncRewake` 和 channel 开关,是否可用要在真会话里试过才算数。
