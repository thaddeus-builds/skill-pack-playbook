# 设计:L4 通用部分(规则起头的工作)

*给负责人看的一页。看完回一句"同意"即可;不同意的地方直接说。没有演示页:这是 `kit/autonomy.py` 里的纯函数,没有界面。SEO 包那边的设计(blog 选题,S254)你已经在 2026-10-30 同意了;这一页只管 playbook 里**通用**的那一半。*

## 它是什么

playbook 的 `docs/autonomy.md` 里,L4 一直写着"没建"。L4 的意思是:**固定规则**选题,agent 不再逐篇请人批,但仍在 L3(你开的模式)里面,且要你单独再开一个开关。

这次建的是**不带任何 SEO 词**的那部分,别的包以后也能用:

| # | 做了什么 | 一句话 |
| --- | --- | --- |
| 1 | 第二个开关 | 值像 `2026-11-30:R01`。要 L3 开着;只有人确认才能打开;agent 只能关;最多 28 天,且不会超过 L3 的到期日 |
| 2 | 新证明 `rule` | 记成 `<用户>@rule`,原因后面带 ` [rule=规则号 basis=依据日期 mode=#开关行号]`;撤回不需要确认码,和 L3 一样 |
| 3 | 合格判断 | 返回"为什么这条规则不能管这次写入",按固定顺序;依据过期、规则两次出错、本周篇数满了,都会停 |
| 4 | 推翻率读取器 | 看某一类工作:开始几个、上线几个、被撤回几个、被改过几个;对照**包自己给的门槛**,达不到就不让确认这个开关 |

## 留在包里的(通用部分不碰)

- **规则本身**:选什么题、读哪些数据、合格的条件。包的登记表,一行一条,每行有测试。
- **上线前的检查**:包自己的事。出错记成一条"出错"事件。
- **数字**:最多几天、每周几篇、推翻率门槛(SEO 的建议:上线 10 篇、最多 1 篇被撤回)。通用部分不设默认值。
- **文字**:每个原因都是代码,包自己登记、自己翻译。

## SEO 包要传进来的

1. 规则登记表的 id 列表,和每条规则当时读的"依据"(日期或哈希),以及现在重算的依据。
2. 开关事实的历史行(和 L3 开关同样的形状)。
3. 从自己的存档映射出的**事件**:`{规则, 条目, 事件, 时间, 类型, 证明}`,事件是 开始 / 上线 / 撤回 / 修改 / 出错。
4. 写入的存档清单(算每周篇数用)。
5. 三个数:最多天数、每周上限、推翻率门槛。
6. 自己的检查结果(一个代码,不过就停)。

## 要你决定的(四件)

| # | 问题 | 我的做法 | 为什么 |
| --- | --- | --- | --- |
| 1 | 什么算"被推翻" | 只数**上线之后**被撤回或被改的条目;上线前改草稿不算;一个条目撤回又改,算一个 | 上线前的修改是你在做稿,不是在推翻规则 |
| 2 | 出错怎么停 | 连续两次出错 → 这条规则关 7 天(从最近一次出错算);中间有一次成功上线就重新数;7 天后立刻再错一次,马上再关 7 天,不给免费重试 | 宁可多关;重开靠人确认也行 |
| 3 | 门槛卡在哪 | 卡在**确认这个开关**的那一刻;打开之后推翻率变高,不会自己关,只会在报告里看到 | 和 L3 一样:升级要人,降级谁都可以 |
| 4 | `autonomy` 包开始引用 `base` 的 `human` | 为了用同一个"依据是否过期"的判断,不再复制一份 | `base` 是所有包都可以引用的 |

## 说实话的限制

- 还没有任何包用它,只用假数据测过。第一个包真正接上时,可能还会发现缺什么。
- 推翻率只数**通过包的门**做的撤回和修改。你直接在站点后台改或隐藏,包看不到(除非包去读)。推翻率低,可能是内容好,也可能是没人看。门槛是你的数字,不等于规则正确;抽查仍然要有。
- 出错只和包的检查一样强:检查永远不过不了,规则就永远不会"出错"。
- 公开出去的内容撤回不了已经被看过、被抓取的部分。

## 风险与它的答案

| 风险 | 答案 |
| --- | --- |
| agent 自己把规则开关打开 | 只有人的确认(终端或转发的确认码)能抬高;`@rule`、`@auto`、`@cli`、`client:` 的行都不算 |
| L3 关了,规则还在跑 | 规则开关读 L3 的状态:L3 关,它也关;到期日取两者较早的 |
| 依据过期了还在按旧数据选题 | 依据对不上(或根本没存)就不合格,这条停在等人批 |
| 本周写太多 | 篇数从存档里数,不用计数器;满了就停,不发任何确认码 |
| 门槛没到就想开 | `may_confirm_rules` 拒绝;关掉永远不拒绝 |
